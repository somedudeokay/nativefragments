Framework evaluation · 29 September 2026 · local review

Keep the core small.
Make its guarantees firm.

Native Fragments has a coherent design for server-rendered applications with persistent UI and selectively updated HTML. Its next milestone should be dependable navigation and request handling.

The framework has a clear reason to exist.

Preserve

  • Useful first-response HTML. Direct routes and native anchors/forms provide a practical fallback.
  • Separate core and Lit. Keep SSR and hydration version coupling inside the Lit adapter.
  • Explicit browser capabilities. The returned router interface is easier to own and dispose than compatibility globals.
  • Native Response escape hatch. Authors can express HTTP behavior without learning another result type.
  • Immediate deferred work. Renderers begin when defer() is called; unrelated data requests can overlap.

Sharpen

  • Positioning. Lead with streaming HTML, persistent shells, and optional Lit interaction. Show the complete direct-load → fragment-update → fallback story.
  • One realistic application. Add an authenticated, database-backed example with mutations and invalidation; small UI demos hide request-lifetime gaps.
  • Measure what matters. Publish first useful HTML, response-to-frame latency, bytes, and hydration work under slow network/CPU conditions.
  • Delay feature expansion. Stabilize navigation, response handling, cache policy, and testing before adding a compiler, state system, or more adapters.

Prioritized architecture candidates.

A deep module hides substantial behavior behind a small interface. These changes improve locality—where the rules and bugs live—and leverage—how much each caller gets from the interface. Dark boxes show the proposed deep module; dashed outlines show its seam. Proposed designs below are directions, not new public contracts.

Give navigation one owner

Before

After · proposed

↓

Problem. The navigation module coordinates fetch subscribers, DOM swaps, view transitions, history, focus, and cancellation without one commit decision.

Evidence. Confirmed in a minimal DOM reproduction: /settings → named panel /settings/profile → Back changes the URL to /settings but leaves the profile panel visible. The popstate fast path compares against the last primary route. Cancellation after a view-transition callback is queued is another case to test; it was not reproduced in Chrome in this review.

Direction. Deepen the private navigation module around a transaction that owns whether a navigation may commit, and how its URL and modified targets are restored. Keep the public interface small.

  • Locality: one commit decision
  • Leverage: every target uses it
  • Test Back, Forward, supersession

Acceptance: primary → named target → Back/Forward; two named targets; slow navigation superseded during a view transition. Run in a real browser.

Before

After · proposed

↓

↓

Problem. The adapter's internal redirect implementation bypasses parts of native response behavior, and error reporting can itself escape the error path.

Evidence. Confirmed against the real adapter: a fragment route returning 302 with Set-Cookie becomes a 200 fragment with no Set-Cookie; the destination also receives the old Cookie header. A throwing createApi onError hook rejects fetch instead of returning its 500 response. These remain unfixed.

Direction. Make one response-handling module own redirect semantics, header propagation, and error fallback. Decide explicitly when the browser must follow a redirect so cookie changes are applied before rendering the destination.

  • Locality: one response policy
  • Leverage: document / fragment parity
  • Test auth redirects end to end

Acceptance: a cookie-setting redirect sees the updated cookie at its destination, nested redirects retain metadata, and a failing error hook cannot break the fallback.

Unify request context for application code

Before

After · proposed

Request-context module
↓

↓

Problem. API handlers receive env and the execution context, while page renderers, metadata, actions, and deferred fragments receive a smaller context.

Evidence. The real adapter reproduction returned env=false inside a route despite passing an environment binding to fetch. Authors must arrange access separately; importing Cloudflare bindings is possible, but it does not provide a common request-scoped seam for tests, authentication, or other adapters.

Direction. Deepen the request-context module so request-scoped bindings and application state are prepared once and carried through rendering, actions, and deferred work. Define the lifetime before adding middleware features.

  • Locality: request setup once
  • Leverage: consistent application interface
  • Tests inject request-scoped values

Acceptance: isolated parallel requests cannot exchange user state, all render paths see the intended bindings, and deferred work shares the same cancellation lifetime.

Make cache policy part of the transport module

Before

Problem. The module retains every completed HTML response in an unbounded Map, while expiry is checked only when reading an entry.

Evidence. Cache insertion does not inspect Cache-Control, and expired entries are not evicted. Redirects also create aliases that are invalidated by key rather than by shared response identity. This is a code-level finding; memory growth and personalized-content behavior were not load-tested.

Direction. Keep cache policy inside the existing transport module: bound retained entries or bytes, prune expired entries, define no-store behavior, and invalidate redirect aliases together.

  • Locality: cache rules together
  • Leverage: safer default prefetch
  • Tests cover memory and freshness

Acceptance: no-store responses do not replay, expired entries are released, repeated unique searches stay bounded, and invalidating a redirect destination removes aliases.

Problem. The public browser interface is verified mainly by a smoke script in a sibling repository, so core changes do not automatically exercise it in release CI.

Evidence. Before this review, the release workflow ran check but no tests. This review added Node tests to release CI and a pull-request workflow, plus focused loader tests. Browser checks still run separately; GitHub Actions itself was not executed here.

Direction. Move or share a self-contained browser contract suite with the framework repository, then test the packed scaffold with the same package artifacts consumers install. Add type-consumer fixtures; declaration generation currently has checkJs disabled.

  • Locality: regressions stay with core
  • Leverage: one reproducible check
  • Tests cross real public seams

Acceptance: Chromium plus WebKit/Firefox navigation, JavaScript-disabled fallbacks, delayed hydration, Worker failure/disposal, and a clean tarball-based scaffold installation.

Problem. Build knowledge is copied across projects, while older instructions still describe zero-build apps and a removed shadow() hydration interface.

Evidence. Current code uses esbuild and the separate Lit adapter. Core AGENTS.md documents this direction, but the docs AGENTS.md still prescribes shadow(). No CONTEXT.md or architecture decision records were found in the inspected checkouts.

Direction. Record the current choices and retire contradictory guidance first. Then consider a small build module shared by the scaffold and maintained applications, only if its interface stays narrower than the duplicated implementation.

  • Locality: policy and fixes align
  • Leverage: scaffold matches examples
  • Preserve standards-based source

Acceptance: a scaffold builds without repository-relative assumptions, browser-worker entries are explicit, and generated assets have a documented caching/versioning policy.

Smaller follow-ups worth scheduling.

  1. Worker lifetime. client/worker.js:102–129 accepts calls after dispose, sending them to a worker whose response listener has been removed. A reproduction timed out rather than rejecting immediately. Add an explicit closed state, transport error handling, and cleanup for failed postMessage calls.
  2. HTML trust documentation. Escaping interpolated text is useful, but the tag is not a contextual HTML sanitizer. Document quoted attributes, URL validation, trusted raw HTML, and safe JSON embedding with executable examples.
  3. Types as a consumer contract. The Cloudflare handler declaration omits the third execution-context argument used by the implementation. Add realistic TypeScript consumer fixtures and audit generated declarations instead of treating successful emission as type checking.
  4. Streaming ownership. Test disconnects and abandoned consumers in workerd. The current Node transport tests prove framing and early output, not all runtime lifetime behavior. Cloudflare's Worker guidance is a useful reference for streaming and request-scoped work.

Assessment: a promising foundation for focused applications, with several demonstrated correctness gaps to resolve before claiming general production readiness. The small runtime is measured; broad speed and reliability claims still need evidence.

Start with the navigation transaction.

It addresses the strongest recurring source of bugs: disagreement between cancellation, rendered content, and history. Preserve the existing public interface and prove it with browser-level scenarios. Treat cookie-preserving redirects as an immediate parallel correctness fix before using authentication flows.
